Why build this?

I want to learn both Clojure and emulation by building something I want to use. This is not just a language exercise, and getting a game running is not the only measure of success.

  • I want to write Lisp by hand and understand its simplicity. The REPL, immutable data, and function composition should become ordinary tools rather than unfamiliar ideas.
  • I want to understand computer science fundamentals that I rarely use in everyday software work. A Game Boy makes CPU registers, instruction decoding, bitwise operations, memory, graphics hardware, and timing concrete.
  • I want to model a machine as data and describe its behavior through functions. Choosing those representations is part of the work, not a decision for the agent to make for me.
  • I enjoy retro games, pixel art, and Metroidvanias. Understanding the hardware behind older games is interesting in its own right.

Do not simplify away either subject. Learn ordinary Clojure idioms while working through the hardware behavior they represent.

V1: one playable ROM

Build a small but real original Game Boy (DMG) emulator in jank. Launch a complete program that loads a legally distributable homebrew ROM, renders its graphics, and accepts keyboard controls. Start with a window and a test pattern, then connect the emulated hardware in small steps.

Aim for 5 to 10 hours of focused effort. That is an ambitious budget, not a guarantee. Spend the time on the foundational behavior needed for one playable ROM rather than the long tail of hardware support.

Use an 80/20 approach without faking the machine. Implement the hardware behavior the target needs according to the specification. Do not hardcode game logic, special instruction addresses, or expected frames to make the ROM appear to work.

First game

Play Game Boy Raw Snake, included at roms/raw-snake/snake.gb.

The playable check is starting from that ROM, passing the title screen, and playing in the window at a usable speed. The board, snake, food, and score should display correctly. You can turn with the keyboard, collect food, collide, and play again.

The learning check is being able to explain the major components and their interactions. I should have written meaningful Clojure myself, chosen the machine-state representation, and checked its behavior against independent references.

Start here

Follow the README to install the tools. Edit src/jankboy/main.jank in your editor and save it. In another terminal, run mise run run. Save and run again after each change.

Change the message printed by -main, save the file, and run it again. Check that you see your new message.

When you want to try expressions interactively, mise run repl opens a REPL. It is optional; you do not need editor integration.

Keep the implementation small

Prefer jank and raylib. Use ordinary, portable Clojure idioms where practical, but check jank's support rather than assuming a JVM library will work. Keep the existing tooling when it works.

Represent hardware state so you can inspect it in the REPL. Use functions to describe changes and compose smaller behaviors. Immutable snapshots can help you reason about a step, but do not force one representation everywhere or optimize before there is a reason.

Keep emulation separate from the host window, keyboard input, and execution controls. You should be able to inspect and test a CPU step without opening a window. Simple functions and data are enough to start; no framework or speculative architecture is needed.

Read first

This guide assumes you can read Scheme-style expressions, but does not assume you have written Clojure. Use these short readings alongside the milestones. Read enough to understand the next small task, then try it in the REPL. You do not need to finish whole books or pass a series of drills first.

1. Clojure syntax and data

Read Syntax, Functions, Sequential collections, and Hashed collections in the Clojure learning guide.

Pay attention to vectors, maps, and keywords. These are ordinary tools for representing state in Clojure. Understand defn, let, and fn, how to look up a value in a map, and how assoc produces an updated map without changing the original. Unlike Scheme, only nil and false are false in a condition; an empty list is true.

If immutable updates are unfamiliar, create a map with two values. Predict what updating one value with assoc will return. Check the returned map and the original in the REPL. Use this to explain how a function can produce a new machine state without changing a previous snapshot.

Leave macros, protocols, and advanced sequence processing for when you need them.

2. The jank REPL and native interop

Use the jank REPL guide when you want to try expressions interactively. For graphics, read the official raylib example and look up its C++ interop forms in the jank book.

jank is a native Clojure dialect, not a JVM runtime. Use the Clojure guide for language fundamentals, but check jank's support before relying on a feature or library.

Before writing graphics code, identify the forms in the example that create a window, draw a frame, and release resources. You do not need to understand every native type yet.

3. The machine you are emulating

Read the Pan Docs introduction, then its Memory map and CPU registers and flags sections. Learn what a byte and a 16-bit address represent, how hexadecimal notation works, and why some memory addresses refer to hardware registers rather than RAM.

Before writing CPU code, be able to explain what the program counter points to and how an instruction changes CPU state. Before writing graphics code, distinguish the host window from the emulated LCD. Read the detailed hardware rules as you reach each milestone.

V1 milestones

Work in sessions of about two to three hours within the 5 to 10 hour target. Get something visual running early. These are observable steps toward the game, not a promise that every step takes the same amount of time.

For each milestone, predict a small result, write the relevant behavior, and check it. Keep useful checks as tests you can rerun. If you get stuck on setup or an obscure compatibility issue, ask for help rather than spending the session on it.

1. Put pixels in a window

The Game Boy screen is 160 × 144 pixels with four shades. raylib provides the host window and keyboard events. Your emulator computes the pixels to display.

Start with the official jank raylib example. Open and close its window before adapting it.

  1. Open and close a blank window.
  2. Draw a fixed pattern using the four shades.
  3. Change the pattern with one key.

At first, you are drawing your own pattern, not emulating video hardware. What would you change to display the same 160 × 144 image at twice the size?

Done when you can display all four shades at an integer scale, change the pattern with a key, and close the window cleanly.

2. Execute and test instructions

The SM83 is the Game Boy's CPU. Its registers hold working values, and its program counter holds the address of the next instruction. Read Pan Docs' instruction-set overview and follow its links to instruction semantics. Use the Clojure flow control guide when you need branching or loops.

Before decoding instructions, practise byte-sized arithmetic in the REPL. Check wraparound, little-endian byte order, and signed relative offsets against the specification. In little-endian order, the low byte of a multi-byte value comes first. Record whether your timing counts use clock ticks (T-cycles) or machine cycles (M-cycles) before comparing them with a reference.

Choose one instruction. Write down its starting state and expected ending state before implementing it. Check your result manually, then write one state comparison you can rerun. Expand to decoding, flags, stack operations, and cycle counts as the target needs them. You do not need a complete opcode table before moving on to memory or graphics.

Use SM83 single-step tests as an independent check. Their flat 64 KB memory model is not the Game Boy memory map. Keep these tests alongside later graphical checks.

Done when you can fetch and execute a short instruction sequence, explain its state changes and cycle counts, and reproduce the results in independent tests. Extend instruction coverage as you work through the later milestones.

3. Load a ROM into mapped memory

Read Pan Docs' cartridge header, memory map, and power-up sequence sections before choosing the loader's checks and initial machine state.

Read and validate the cartridge header. Support ROM-only cartridges first and report unsupported types clearly. Map ROM, work RAM, video RAM, sprite memory (OAM), and hardware registers according to Pan Docs. Start from a documented DMG post-boot state without distributing a boot ROM. The CPU reads instructions and data through this memory map.

Done when the header identifies the target cartridge, ROM reads return the file's bytes, RAM writes can be read back, and unsupported cartridge types produce a clear error.

4. Render emulated graphics

Read Pan Docs' tile data, background maps, OAM, and LCD control and palette register sections.

Replace the test pattern with pixels computed from emulated video memory and LCD registers. Tile data describes pixel shades; tile maps select which tiles appear on the background. OAM describes sprite positions and attributes.

Implement backgrounds and palettes, then the sprite behavior needed by the target. Follow the hardware rules for each feature you support, but defer unused modes and accuracy edge cases. Check small examples before comparing the game's title screen.

Done when small video-memory examples produce the expected shades and positions, palette changes affect the image, and backgrounds and sprites combine correctly for the target.

5. Connect timing and controls

Read Pan Docs' rendering, timer and divider registers, interrupts, and joypad input sections. Check the specified timing and button bit values rather than guessing from what appears to work.

Advance the LCD and divider from CPU cycles. Implement the scanline, VBlank, and interrupt behavior the target relies on. Use documented timing, but leave cycle-perfect accuracy and unused access quirks for V2. Map arrows to the D-pad, Z/X to A/B, Enter to Start, and Backspace to Select through the emulated joypad register and its interrupt behavior. Keep host frame pacing separate from emulated timing.

Test interrupt servicing as well as interrupt requests. Check that a pending enabled interrupt saves the return address, enters the correct vector, and can return to the interrupted code. The LCD and divider must keep advancing while the CPU is halted.

Done when a known number of CPU cycles produces the expected LCD and divider state, button presses and releases produce the specified joypad values, and the CPU services interrupts and resumes execution.

6. Play the target ROM

Integrate these pieces and fill hardware gaps using Pan Docs and focused tests. Compare the title screen and gameplay with a trusted emulator. Check the success criteria above, including repeated turns and restarting after a collision. Implement hardware rules rather than special cases for the game's code or instruction addresses.

If an obscure detail threatens the time budget, decide with the agent whether to explain it, delegate a narrow fix, or defer it. Preserve your understanding of the CPU, memory, and graphics relationship. You do not need to handwrite every repetitive detail to earn a playable result.

Done when you can pass the title screen, steer the snake, collect food, see the score change, and play again after a collision without graphical corruption or missed controls.

V2 and optional experiments

After V1, choose improvements based on what you want to understand or play next. These are possibilities, not required follow-up work.

  • Add audio or save states.
  • Support more cartridge types and a wider range of games.
  • Improve timing accuracy and hardware edge cases using focused test ROMs.
  • Measure performance before changing data representations or optimizing hot paths.

Understanding the Game Boy

  • Pan Docs is the main hardware reference for the CPU, memory map, graphics, timers, and joypad.
  • SM83 single-step tests provide instruction inputs and expected CPU states.

For implementation help after your own attempt, compare a small relevant part of a working emulator rather than copying its architecture. The Clojure Game Boy emulator write-up discusses memory modeling, and SameBoy is a mature implementation to consult for difficult behavior. Neither replaces the hardware specification.

Getting help

The agent is a knowledgeable tutor and a pragmatic pair programmer. You personally model the machine state and implement the interesting parts of instruction interpretation, memory behavior, and the CPU's relationship with graphics.

Ask when you cannot predict the next small result, cannot find a hardware rule, or get a result that differs from your prediction. Share your attempt, expected result, and actual result. Start with a hint or explanation, then ask for stronger guidance if you need it. The point is understanding and progress, not completing tedious exercises.

With your permission, the agent can handle tooling, boilerplate, repetitive implementation, or obscure compatibility work that adds little to the lesson. Agree on that boundary first, review what changed, and keep meaningful Clojure and emulation decisions in your hands. The agent must not simply generate a working emulator for you.
